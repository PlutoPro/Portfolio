Introducing Cloud Cache: A Multi-Tenant Key-Value Store in Rust

November 19, 2026

QuickCache taught me how a cache server works at its core. The next question was what it takes to run one for real: shared by a team, secured with real logins, and spread across several servers behind a load balancer. So I built Cloud Cache, an open-source key-value store written in Rust. It keeps each organization's data separate, speaks both HTTP and TCP, and checks every request against the identity provider you already use.

The idea

Most caches leave security to you. You put them on a private network and hope nothing else gets in. I wanted a cache where every request carries a real login token, issued by an identity provider like Keycloak, Auth0 or Microsoft Entra ID, so the cache knows who is asking and what they're allowed to do.

I also wanted it to work for teams. In Cloud Cache, every key belongs to an organization. Everyone in that organization shares its keys, and nobody outside it can see them, even if they ask for the same key name.

How it works

Cloud Cache is built on Rust's tokio runtime, with axum for the HTTP side. Each server holds its keys in memory and offers two ways in. The HTTP API treats a key as a URL and the value as the request body. The TCP API is a line-based protocol in the same spirit as QuickCache, but every connection has to sign in first:

  • AUTH <token> signs the connection in with an access token.
  • SET <key> <value> stores a value under a key.
  • SETEX <key> <seconds> <value> stores a value that expires on its own.
  • GET <key> returns the value stored under a key.
  • DEL <key> removes a key.

A TCP session only lasts as long as the token that opened it. When the token expires, commands return an error until the client sends AUTH again with a fresh one, without having to reconnect.

Checking tokens is split into two separate jobs. The first is making sure a token is genuine: the signature, who issued it, who it's for and when it expires. That part is standard and the same for every provider. The second is working out what the token means: which roles the person has and which organizations they belong to.

Every provider puts that information in a different place, so Cloud Cache ships with presets for Keycloak, Auth0, Entra ID, Zitadel and a single-team mode, and any of them can be adjusted with settings. Because the servers download the provider's signing keys once and check tokens themselves, there's no extra round trip to the provider on each request.

It's also built to sit behind a load balancer. A server only reports itself ready once it can verify tokens, and when it's shutting down it stops taking new traffic before it closes, so requests aren't dropped. The project includes an HAProxy setup that sends each key to the same server every time. There's also a web dashboard, built with Next.js, where people can browse and edit their organization's keys, see their usage and manage who's on their team.

Trying it out

The whole setup runs with Docker Compose: Keycloak for logins, three Cloud Cache servers, HAProxy in front of them and the dashboard. Give Keycloak 30 to 60 seconds to start, then open http://localhost:3100 and sign in as alice with the password alice.

$ git clone https://github.com/PlutoPro/Cloud-Cache
$ cd Cloud-Cache/deploy
$ docker compose up --build

To use the TCP API, get a token from Keycloak first, then talk to the cache with Netcat:

$ curl -s localhost:18081/realms/kv/protocol/openid-connect/token \
    -d grant_type=password -d client_id=kv-cli \
    -d username=alice -d password=alice | jq -r .access_token
eyJhbGciOiJSUzI1NiIs...
$ nc localhost 17379
AUTH eyJhbGciOiJSUzI1NiIs...
OK alice 6f1d2c3b-aaaa-4bbb-8ccc-000000000001
SET greeting hello there
OK
GET greeting
VALUE hello there
QUIT
BYE

The long ID after alice is her organization. Anything she stores lands in that organization's keyspace, and the same key is readable over HTTP with the same token.

What I learned

The biggest lesson was that tests against fake services only go so far. The automated tests use a mock identity provider, and they caught a lot. But several bugs only showed up when I ran everything against a real Keycloak and clicked through the dashboard in a real browser. Keycloak, for example, sent organization information in a different shape than I expected, mixing two formats into one list.

My favorite bug was one where nothing looked wrong. The dashboard was supposed to quietly renew people's logins before they expired, but it never did. I had named my expiry field exp, and the encrypted cookie that stores the session uses a field with the same name for its own expiry, which silently overwrote mine. People only stayed signed in because the servers allow 30 seconds of leeway on expiry. It surfaced only when I shortened the login lifetime and checked whether the cookie actually changed. Now I try to test the exact thing I care about, not something that merely looks like it.

Details matter in security code, too. Cloud Cache used to trim trailing slashes from the identity provider's address, which looked like harmless tidying. But Auth0's address ends in a slash, and tokens have to match it exactly, so every Auth0 login would have been rejected.

What's next

Cloud Cache works today, but data only lives in memory and each server holds its own share of the keys. The roadmap is about making it a cache you can depend on:

  • Request forwarding so any server can answer for any key, and the cluster behaves like one cache.
  • Persistence, writing data to disk so it survives a restart.
  • Replication, keeping copies of each key on more than one server.
  • Per-organization limits on how much memory each team can use.
  • More identity providers for team management in the dashboard, starting with Auth0 and Entra ID.

Cloud Cache is open source. The code is available on GitHub if you want to try it, follow along as it grows or contribute.
