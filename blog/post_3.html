Introducing QuickCache: A Key-Value Cache Server in Python

November 19, 2026

Caches like Redis and Memcached sit behind a huge share of the applications we use every day. They keep frequently used data in memory so it can be served fast, without a round trip to a database. I wanted to understand how a server like that works at its core, so I built my own: QuickCache, a lightweight, asynchronous in-memory key-value cache server written in Python.

The idea

QuickCache is deliberately small. It talks over raw TCP sockets instead of HTTP, uses a plain-text command protocol, and is built entirely on Python's standard library. There are no external dependencies to install. If you have Python 3.7 or newer, you can clone it and run it.

How it works

The server is built on Python's asyncio library. Rather than spinning up a new thread for every client, a single event loop handles all of the connections at once. Each client gets its own handler that reads commands, acts on an in-memory dictionary, and writes a response back. Using asyncio this way means many clients can be connected at the same time without blocking one another.

The protocol is just as simple. Each command is a space-separated line of text ending in a newline. QuickCache currently supports four commands:

  • SET <key> <value> stores a value under a key.
  • GET <key> returns the value stored under a key.
  • DEL <key> removes a key from the cache.
  • LIST returns every key and value currently stored.

Trying it out

Start the server with python main.py and it listens on 127.0.0.1:8888. Because it speaks plain TCP, you don't need a special client. Netcat works fine:

$ nc 127.0.0.1 8888
SET user_101 active
OK: user_101 set to active
GET user_101
user_101: active
DEL user_101
OK: user_101 deleted
GET user_101
user_101: Key not found

What I learned

Building QuickCache made it clear how much a "simple" cache server has to think about. Even with a handful of commands, the server has to parse input it can't trust, respond with clear errors when a command is malformed, and clean up properly when a client disconnects unexpectedly. Writing the protocol myself also showed me why real systems like Redis put so much care into how their commands are framed.

What's next

QuickCache does the basics today, and the roadmap is about turning it into something closer to a real cache:

  • Key expiration (TTL) so entries can expire on their own.
  • Richer values, including values with spaces and JSON payloads.
  • Persistence, snapshotting the cache to disk so data survives a restart.

The code is available on GitHub if you want to try it or follow along as it grows.
