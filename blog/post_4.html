Async in Python

Exploring Asynchronous Programming in Python

November 19, 2026

When I built QuickCache, my key-value cache server, I needed it to handle more than one client at a time. That requirement pushed me into Python's asyncio library, and asynchronous programming turned out to be one of the most interesting parts of the whole project. This post covers what I learned along the way.

The problem: waiting

Most of what a network server does is wait. It waits for a client to connect, waits for data to arrive, and waits for a response to finish sending. In ordinary synchronous code, every one of those waits blocks the whole program. If one client is slow to send its next command, every other client is stuck behind it.

The traditional fix is to give each client its own thread. That works, but threads carry memory overhead, and code that shares data between threads has to be careful about locking. Asynchronous programming takes a different approach.

The event loop

At the center of asyncio is the event loop. It runs on a single thread and keeps track of many tasks at once. Whenever a task reaches a point where it has to wait, such as reading from a socket, it hands control back to the loop. The loop then runs whichever task is ready to make progress. When the data the first task was waiting for arrives, the loop picks it back up where it left off.

Nothing actually runs in parallel. The program is simply never sitting idle while there is other work it could be doing. For I/O-heavy programs like servers, that is usually all you need.

async and await

Python expresses this with two keywords. Defining a function with async def makes it a coroutine, a function that can pause and resume. Inside it, await marks the spots where it is allowed to pause and let other tasks run.

import asyncio

async def fetch(name, delay):
    print(f"{name} started")
    await asyncio.sleep(delay)   # pause here, let others run
    print(f"{name} finished")

async def main():
    await asyncio.gather(
        fetch("A", 2),
        fetch("B", 1),
    )

asyncio.run(main())

Both tasks start right away, B finishes first, and the whole program takes about two seconds instead of three. That is the core idea in a few lines: while one task waits, another one runs.

How QuickCache uses it

QuickCache starts its server with asyncio.start_server, which calls a handler coroutine for every client that connects. Each handler loops on await reader.read(...) to wait for the next command, updates the in-memory dictionary, and sends back a response with writer.write followed by await writer.drain(). The drain call matters: it pauses the handler if the outgoing buffer is filling up faster than the client can receive it, which keeps one slow client from eating up memory.

Because every wait is an await, dozens of clients can be connected at once on a single thread, each one paused until it has something to say.

Lessons and gotchas

  • Blocking calls freeze everything. A regular time.sleep() or a blocking library call inside a coroutine stops the entire event loop, not just that task. In async code you need the async versions, like asyncio.sleep().
  • async is not automatically faster. Marking a function async only helps if it actually awaits something. A coroutine that just looks up a value in a dictionary gains nothing from being async; it simply adds a little overhead.
  • It is built for I/O, not heavy computation. Async shines when a program spends its time waiting on networks or disks. CPU-heavy work still runs on one thread and will block the loop, so that kind of work belongs in a separate process or thread pool.
  • TCP is a stream, not a list of messages. Reading a fixed number of bytes does not guarantee you get exactly one command. Reading line by line with reader.readline() is a more reliable way to frame a newline-based protocol, and it is on my list of improvements for QuickCache.

Wrapping up

Asynchronous programming felt strange at first, but building a real server with it made the model click. Once you see that the event loop is simply juggling tasks that are waiting, async and await stop looking like magic. I plan to keep building on these ideas as QuickCache grows, starting with key expiration, which is a natural fit for scheduled async tasks.
